# Engineering Report — M1.2: Selection Resolution Engine

**Status:** Complete
**Package(s):** `selection.engine`; additive changes to `selection.model` and `selection.geometry`
**Depends on:** `selection.model` (M1.0), `selection.geometry` (M1.0, via a small shared-utility extraction), `selection.textlayout` (M1.1, read-only)
**Depended on by:** future `ui.reader` wiring (not part of this milestone)

---

## 1. Objectives

Implement the layer of the Selection Engine that resolves a completed lasso
`SelectionPolygon` against a page's `PageContentLayout` into a final
`SelectionResult` — selected text, matched blocks, bounding polygon, and
bounding rectangle — using `SpatialGridIndex` for broad-phase lookup and an
accurate polygon–text intersection algorithm for the narrow phase, with a
configurable overlap threshold and preserved document reading order. No
text layout changes, no OCR, no backend communication, no UI wiring.
Success criterion: given a polygon and a layout, the engine resolves final
selected text with no UI involvement.

## 2. Architectural Decisions

- **Block quad as the clip polygon, lasso as the subject — not the other way
  around.** Sutherland–Hodgman clipping only produces a correct result when
  the *clip* polygon is convex; a freehand lasso is routinely concave and
  sometimes self-intersecting, while a `TextContentBlock.quad` is always
  exactly four corners of a (possibly rotated) rectangle — always convex.
  `PolygonClipper.clip` is therefore always called with the block's quad as
  `convexClip` and the lasso as `subject`. This is the single
  correctness-critical decision in the narrow phase; documented prominently
  in `PolygonClipper`'s KDoc and at its one call site in `SelectionEngine`,
  since reversing the two arguments would silently produce wrong results for
  any non-convex lasso shape without throwing or otherwise signaling an error.
- **Winding-robust clipping.** Rather than requiring callers to normalize
  `convexClip`'s vertex order, `PolygonClipper` detects winding from the
  clip polygon's own signed area and adapts its inside/outside test
  accordingly — one fewer invariant every future caller has to remember to
  uphold.
- **Overlap ratio, not containment.** Per the approved design, a block is
  included if the lasso covers at least `SelectionEngineConfig.minOverlapRatio`
  (default 0.35) of the block's *own* area — not if the block is fully
  enclosed. This matches how people actually draw a lasso: circling around
  text, rarely tracing a shape that perfectly contains every glyph.
- **Configurable threshold as a method parameter, not a Hilt-injected
  value.** `SelectionEngineConfig` is a plain data class passed to
  `SelectionEngine.resolve(...)` with a default value, rather than made
  Hilt-injectable. Hilt's `@Inject constructor` requires every constructor
  parameter to resolve through the dependency graph; a bare `Float` has no
  natural binding without adding a `@Provides` method purely to support one
  tunable number — avoided as unwarranted DI machinery. Ordinary Kotlin
  default-argument semantics on a plain method achieve the same
  "configurable, but simple by default" outcome with zero new Hilt surface.
- **`SelectionResult`/`MatchedBlock` placed in `selection.model`**, per the
  original approved design's own table (§4.1) — unlike `PageContentLayout`
  in M1.1, these reference only existing `selection.model` types
  (`SelectionPolygon`, `ContentBlock`, `NormalizedRect`), so no purity
  refinement was needed here; the model layer's zero-dependency-on-other-layers
  property holds without adjustment.
- **Reading order via a dedicated, polymorphic comparator with a documented
  fallback.** `ReadingOrderComparator` sorts by a `TextContentBlock`'s own
  `(lineIndex, readingOrderIndex)` — the true order PDFBox determined during
  extraction — and falls back to position-based ordering (top-to-bottom,
  then left-to-right, via the shared `boundingBox()`) for any `ContentBlock`
  subtype without that information. This is what lets future image/OCR/
  handwriting blocks (declared in M1.1, still unconstructed) participate in
  a sorted selection the moment something starts producing them, with zero
  change to this comparator or to `SelectionEngine` — directly satisfying
  requirement 9.
- **Duplicate logic eliminated at the source, not worked around.**
  `PolygonBuilder` (M1.0) had a private `signedArea` function computing
  exactly the shoelace formula the new engine also needs for overlap-area
  computation. Rather than write a second copy in `selection.engine`,
  `signedArea` was extracted into a shared `List<NormalizedPoint>.polygonArea()`
  extension in `selection.model` (alongside the `boundingBox()` extension
  already shared since M1.1), and `PolygonBuilder` was refactored to call
  it — removing its private version entirely. Both `PolygonBuilder`'s
  degenerate-shape check and `SelectionEngine`'s overlap-ratio computation
  now call the same single implementation.

## 6. Known Limitations

- Self-intersecting lasso strokes (not explicitly prevented by M1.0's
  `PolygonBuilder`, which only rejects near-zero area and too-few vertices)
  can, in principle, cause `PolygonClipper`'s output to be a technically
  malformed polygon for pathological input shapes. In practice, minor
  self-crossings from careless drawing tend to affect area calculations
  negligibly; large-scale self-intersection (e.g. a deliberate figure-eight)
  is an accepted, documented edge case rather than a solved one — the same
  category of caveat flagged in the original approved design's own "Edge
  Cases" section.
- `MIN_BLOCK_AREA` (the degenerate-block guard in `SelectionEngine`) is a
  fixed internal constant, not part of `SelectionEngineConfig` — only the
  overlap ratio was required to be configurable per the milestone's
  requirements, so this was deliberately left as an implementation detail
  rather than surfaced as a second tunable.
- No wiring into `ReaderViewModel`/`ReaderScreen` exists yet — `SelectionEngine`
  is reachable only by direct dependency injection, exactly as scoped.

## 7. Risks

- The Sutherland–Hodgman implementation and winding-detection logic were
  verified by manual trace against the standard algorithm, not by executing
  unit tests against a live build (unavailable in this sandbox). This is
  the highest-value candidate for an actual JVM unit test suite once a real
  build is available, since `selection.engine`, `selection.geometry`, and
  `selection.model` are all pure Kotlin and fully unit-testable without
  Android instrumentation.
- The default `minOverlapRatio` (0.35) is carried over from the original
  design's suggested range and is not yet validated against real user
  drawing behavior — worth tuning once this engine is wired into the UI and
  observable end-to-end.
