# Engineering Report — M1.1: Text Layout Engine

**Status:** Complete
**Package(s):** `selection.textlayout`; additive changes to `selection.model`
**Depends on:** `selection.model` (M1.0), `data.repository.PdfRepository` (frozen, read-only)
**Depended on by:** M1.2 (`selection.engine`, polygon–text intersection)

---

## 1. Objectives

Implement only the text layout layer of the Selection Engine: extract
embedded PDF text together with accurate, normalized bounding boxes; build a
spatial index for fast region lookup; cache page layouts with an LRU
strategy; and expose all of it behind a content-source-agnostic interface —
with **no** polygon intersection, text selection, OCR, or backend
communication in this milestone. Success criterion: the application must be
capable of producing a `PageContentLayout` containing normalized text blocks
for any PDF page.

## 2. Architectural Decisions

- **`ContentBlock` sealed hierarchy added to `selection.model`**: `TextContentBlock`
  (populated this milestone), plus `ImageContentBlock` and
  `HandwritingStrokeBlock` (declared now, constructed by nothing yet) — so
  that `PageContentLayout`, `SpatialGridIndex`, and the future intersection
  engine are all written once, generically, against the common base type.
  Adding OCR/image/handwriting support later means adding data to
  already-existing branches of a `when`, not restructuring these components.
- **`PageContentLayout` placed in `selection.textlayout`, not `selection.model`**:
  a deliberate, narrow refinement of the original design sketch (which
  informally listed it under `model`). Because it bundles a
  `SpatialGridIndex` — a textlayout-layer concept — keeping it out of
  `selection.model` preserves that package's stricter, verified property of
  zero dependency on any other Selection Engine layer.
- **Broad-phase-only spatial index**: `SpatialGridIndex` performs uniform-grid
  bucketing and bounding-box-overlap candidate lookup only. It explicitly
  does not perform polygon clipping, overlap-ratio computation, or any
  narrow-phase geometric test — that work is reserved for the M1.2
  intersection engine, which will consume `candidatesNear`'s output as its
  input rather than duplicating this lookup.
- **`PageContentProvider` as the content-source abstraction**: both
  `PositionedTextExtractor` and `TextLayoutCache` implement this interface,
  which takes `(pdfId, pageIndex)` and returns a `PageContentLayout`. This is
  the extension point future OCR/handwriting sources plug into without any
  change to whatever eventually consumes a `PageContentLayout`.
- **Frozen repository reused, not modified**: `PositionedTextExtractor`
  resolves `pdfId → filePath` by depending on the existing, unmodified
  `PdfRepository` — exactly as `ReaderViewModel` already does elsewhere in
  the codebase. No repository, networking, or authentication code was
  touched.
- **Cache depends on the concrete extractor, not the abstract interface**:
  with only one `PageContentProvider` implementation existing yet,
  introducing a Hilt `@Binds` module now would be premature abstraction.
  Both classes already implement the same interface, so a future second
  provider (OCR) can be composed in without restructuring `TextLayoutCache`.
- **Coordinate normalization reuses PDFBox's rotation-adjusted glyph
  coordinates** (`xDirAdj`/`yDirAdj`/`widthDirAdj`/`heightDir`), dividing by
  the page's *displayed* (rotation-swapped) width/height, landing every
  extracted word directly in the same normalized `(u,v) ∈ [0,1]²` space
  `NormalizedPoint`/`SelectionPolygon` already use from M1.0 — no second
  coordinate system was introduced.
- **Duplicate logic removed proactively**: `SelectionPolygon.boundingBox()`
  (M1.0) had an inline min/max-tracking loop that `ContentBlock`'s
  bounding-box needed identically. Extracted a shared
  `List<NormalizedPoint>.boundingBox()` function and refactored
  `SelectionPolygon` to call it, so this logic exists exactly once.

  already-working `pdf/PdfTextExtractor`, but are unverified against a real
  build.

## 6. Known Limitations

- `lineIndex` increments once per `PDFTextStripper.writeString` callback,
  which can occasionally fire more than once for a single visual line (e.g.
  a font change mid-line) — an inherent characteristic of this extraction
  technique. Not used by any M1.1 logic (recorded for a future milestone's
  reading-order assembly only), so this is an acceptable simplification, not
  a defect against this milestone's success criteria.
- No polygon–text intersection, no selection-text generation, no OCR, and no
  `ReaderViewModel`/`ReaderScreen` wiring exist yet — all explicitly out of
  scope this milestone.
- `SpatialGridIndex.candidatesNear` returns bounding-box-overlap candidates
  only, by design; future consumers must not treat its output as a final
  intersection result.

## 7. Risks

- PDFBox rotation/coordinate-adjustment assumptions are standard and
  well-precedented but unverified against a real device/build; the first
  on-device test should specifically check word bounding boxes on a rotated
  (90°/270°) page.
- `TextLayoutCache`'s 5-entry cap is a reasonable default per the approved
  design but untuned against real usage; worth revisiting once
  intersection/selection makes cache hit-rate observable.

## 8. Next Milestone

M1.2 — Polygon–Text Intersection Engine (`selection.engine.SelectionEngine`):
consume a finalized `SelectionPolygon` (M1.0) and a `PageContentLayout`
(M1.1, via `TextLayoutCache`) to produce a `SelectionResult` — the first

Sutherland–Hodgman narrow-phase intersection over `SpatialGridIndex.candidatesNear`'s
broad-phase output.
