# Engineering Report — M1.4: Performance Optimization

**Status:** Complete
**Files touched:** `selection.capture` (1 file), `selection.geometry` (3 files), `selection.textlayout` (2 files), `selection.engine` (2 files), `ui.reader` (2 files) — 10 files total, all pre-existing, none created
**Depends on:** M1.0–M1.3, reused exactly as implemented — no architectural change to any of them
**Behavioral change:** none. Every fix in this milestone either reduces allocation/CPU cost for the same output, or corrects a race/cancellation bug that could produce **stale** state — never a change to correct-case output.

---

## 1. Objectives

Optimize the entire lasso selection pipeline — capture, geometry,
text-layout caching, spatial indexing, and the resolution engine — for
production-scale PDF documents, per the twelve focus areas in the milestone
brief. No new features, no architectural changes, no modification to
networking, authentication, or repositories. Every existing behavior must
be preserved exactly; only speed and memory characteristics may change.

## 2. Approach

Per the lighter-weight workflow now in effect, this milestone touched only
the files directly implicated by "the lasso selection pipeline" — the
capture/geometry/textlayout/engine packages plus their two integration
points in `ui.reader`. No other package was re-read or re-audited; M1.0–M1.3
are assumed correct except where this milestone's own focus areas required
revisiting them.

## 3. Changes by Focus Area

**1. Minimize allocations during lasso drawing** — `LassoGestureController`:
replaced a capturing lambda (`firstOrNull { it.id == downPointerId }`),
which allocated a new closure on every pointer-event iteration for the
whole duration of a drag, with a manual indexed loop; the captured-points
list is now pre-sized (`ArrayList(128)`) instead of growing from empty.
`StrokeSimplifier`: the recursive Ramer–Douglas–Peucker implementation
previously allocated two new lists (`dropLast` + `+`) at *every* recursive
split; rewritten as an equivalent index-marking algorithm (a shared
`BooleanArray` of points-to-keep, walked by index-range recursion instead of
list slicing) that allocates exactly twice per call regardless of stroke
length or recursion depth, with identical output. `CoordinateMapper`:
removed a `Pair<Float, Float>` return value that boxed two floats on every
single point mapped, by inlining the two transform steps into one function.
`PolygonBuilder`: the dedup result list is now pre-sized to the input
length (dedup only ever removes points).

**2. Reduce unnecessary Compose recomposition** — `ReaderScreen`: the
`onLassoStrokeCaptured = viewModel::onLassoStrokeCaptured` argument passed
to `ZoomablePdfPage` was a bound method reference re-evaluated (and thus
reallocated) on every recomposition of `ReaderScreen`'s body — including for
state changes unrelated to the lasso pipeline (e.g. a highlight added
elsewhere) — which could defeat `ZoomablePdfPage`'s recomposition-skipping
even when none of its own inputs actually changed. Wrapped in
`remember(viewModel) { ... }` to give it stable identity across
recompositions for the screen's lifetime.

**3 & 9. Warm/reuse TextLayoutCache efficiently; review cache sizing and
eviction** — Found and fixed a genuine race: `getContentLayout`'s
check-then-fetch-then-store sequence held the mutex only for the individual
map read and the individual map write, not the whole operation, so two
concurrent misses for the same page (the M1.3 per-page prefetch racing an
on-demand lasso lookup, which routinely happens if a user draws a lasso
immediately after a page loads) could each independently run
`PositionedTextExtractor` — duplicate PDFBox parsing of the same page. Now
the mutex is held across the full miss path, so concurrent requests for the
same key serialize onto one extraction rather than duplicating it; cache
*hits* are unaffected (still a brief, effectively-uncontended lock for a map
lookup). Cache size reviewed and widened from 5 to 8 entries — still a
small, bounded, strict-LRU window ("current page ± neighbors"), just wide
enough to better tolerate a reader flipping across a few pages and back.

**4. Improve SpatialGridIndex lookup efficiency** — Added a single-cell fast
path: when a query's bounding box touches exactly one grid cell (the common
case for a modestly sized lasso against the existing 20×20 grid), that
cell's bucket list is returned directly. `build()` never adds a block to
the same cell twice, so a single bucket is already duplicate-free, making
the previous `LinkedHashSet` allocation + `addAll` + `toList()` copy
unnecessary for this case; the multi-cell path (still needing dedup across
merged buckets) is unchanged.

**5 & 11. Eliminate unnecessary object creation / duplicate computations in
SelectionEngine** — `resolve()` was calling `polygon.boundingBox()` twice
per call (once for the broad-phase query, again for the result's
`boundingRect`) — an identical, redundant O(vertex count) scan over an
unchanged polygon. Computed once, reused for both. `PolygonClipper`'s
per-edge clip result list is now pre-sized (bounded by input size + 1 in the
overwhelming common case), reducing growth-reallocation in what runs four
times per candidate block.

**6, 7 & 10. Cancel obsolete work immediately; audit dispatcher switches;
structured concurrency** — Found and fixed a real bug: `onLassoStrokeCaptured`'s
and `loadPage`'s `catch (e: Exception)` blocks would also catch
`CancellationException` (a subclass of `Exception`) without rethrowing it —
a classic structured-concurrency pitfall. Concretely, this meant a
*cancelled* resolution (superseded by a newer stroke, a tool switch, or a
page change — exactly the scenarios `selectionResolutionJob?.cancel()` was
introduced in M1.3 to handle) could still run its cleanup/error-handling
body, racing with and potentially overwriting the *newer* coroutine's
already-applied state. Both catch sites now explicitly catch and rethrow
`CancellationException` before the general `Exception` handler. Separately,
the M1.3 per-page prefetch coroutine was launched fire-and-forget (wrapped
in `runCatching`, which has the same swallows-`CancellationException`
problem) with no `Job` reference at all, so flipping pages quickly left
superseded prefetches for already-abandoned pages running to completion
instead of being cancelled — it's now tracked in a `prefetchJob` field,
cancelled alongside `selectionResolutionJob` at the top of `loadPage`
(focus area 6, "page changes"), with the same explicit
`CancellationException` rethrow. Dispatcher usage itself was audited and
found already correct (CPU-bound geometry/engine work on `Dispatchers.Default`,
PDFBox I/O encapsulated behind `Dispatchers.IO` inside the extractor/renderer
it belongs to, no redundant switching introduced anywhere) — no change
needed there.

**8. Ensure large PDFs remain responsive** — Addressed structurally by the
above: the cache-race fix prevents duplicate large-PDF-page parsing under
concurrency, the `SpatialGridIndex` fast path keeps broad-phase lookup cheap
regardless of page density, and none of the geometry-pipeline allocation
reductions depend on document size (per-stroke cost, not per-document).

**12. Preserve all existing behavior** — See the audit in §4: every change
was verified to produce identical output to its pre-M1.4 counterpart (RDP
simplification, coordinate mapping, cache results, spatial query results,
selection resolution) or to only affect the *timing/ordering* of already-
intended cancellation, never a correct-case result.

## 4. Verification Performed

- Manually traced the rewritten RDP algorithm (`StrokeSimplifier.markKeep`)
  against the original recursive-subList version to confirm identical
  output: both keep exactly the points where perpendicular distance exceeds
  epsilon, recursively, with the same base case and the same treatment of
  the shared boundary point at each split.
- Manually traced `CoordinateMapper.map`'s inlined version against the
  original two-function version to confirm identical arithmetic, just
  without the intermediate `Pair`.
- Confirmed `SpatialGridIndex`'s single-cell fast path is only reachable
  when `minCol == maxCol && minRow == maxRow`, and confirmed (from `build()`'s
  own loop structure) that a single bucket cannot contain a duplicate block
  reference, so skipping the `LinkedHashSet` dedup for that case is safe.
- Confirmed `TextLayoutCache`'s widened mutex scope still uses `withLock`'s
  inline nature correctly for the `return@withLock` early-exit on a cache
  hit (same pattern already verified safe in the M1.1 audit for a
  structurally identical case).
- Confirmed every constructor signature touched this milestone
  (`StrokeSimplifier`, `CoordinateMapper`, `PolygonBuilder`, `TextLayoutCache`,
  `SelectionEngine`, `PolygonClipper`, `ReaderViewModel`) is byte-identical
  to its pre-M1.4 state — zero new dependencies, zero new Hilt wiring.
- Confirmed `ReaderUiState`'s field set (12 fields) and `ReaderScreen`'s
  public composable signature are unchanged from M1.3.
- Project-wide-scoped (to the 10 touched files only, per the current
  workflow) unused-import scan: clean.
- Caught and fixed, during self-review before finalizing: a redundant
  second `prefetchJob?.cancel()` call immediately before relaunching it in
  `loadPage` — harmless (nothing could set the field in between, since
  there's no suspension point separating the two calls) but genuinely
  duplicate, removed.
- No live Gradle/compiler build was possible in this sandbox; all
  verification was via direct source review and manual algorithm tracing,
  consistent with every prior milestone.

## 5. Known Limitations

- None of these changes were benchmarked (no build environment available in
  this sandbox) — the allocation-reduction rationale is based on standard,
  well-understood JVM/Kotlin allocation costs (list growth reallocation,
  lambda capture, tuple boxing), not measured before/after profiling. The
  first on-device pass should specifically compare drawing smoothness and
  GC frequency during an active lasso stroke against the pre-M1.4 build.
- The `TextLayoutCache` mutex-scope widening trades a small amount of
  potential cross-page parallelism (two *different* pages' cache misses now
  serialize against each other, not just same-page misses) for eliminating
  the same-page duplicate-extraction race. Given this app's single-page-at-
  a-time interaction model, this is expected to be a strict improvement in
  practice, but it is a real, deliberate tradeoff worth knowing about if a
  future milestone ever introduces genuine multi-page-concurrent access
  patterns.

## 6. Risks

- The structured-concurrency fixes (explicit `CancellationException`
  rethrow) are the highest-value, highest-confidence correctness fix in
  this milestone, but they were verified by reasoning through Kotlin
  coroutines' cancellation semantics, not by writing and running a
  cancellation-race test. This is the single most important thing to
  exercise on first on-device testing: rapidly draw a lasso, then
  immediately flip pages or switch tools, several times in a row, and
  confirm the UI never shows a stale/mismatched selection.
- The RDP rewrite, while carefully traced for equivalence, is a genuine
  algorithm-implementation change (not just a wrapper/config tweak) inside
  a frozen-architecture package; it should be the first thing checked if
  any lasso-shape-fidelity regression is ever reported.

## 7. Next Milestone

No further Selection Engine milestone is currently scoped. If profiling
after a real build surfaces additional hotspots not covered by this pass
(e.g. `PositionedTextExtractor`'s per-word `TextContentBlock` allocation on
very text-dense pages), that would be a natural, narrowly-scoped follow-up
performance milestone rather than a reason to revisit this one.
