# Engineering Report — M1.3: Selection Integration

**Status:** Complete
**Package(s):** `ui.reader` only (`ReaderViewModel.kt`, `ReaderScreen.kt`)
**Depends on:** `selection.capture`, `selection.geometry`, `selection.textlayout`, `selection.engine` — all M1.0–M1.2, reused exactly as implemented, zero modifications
**Depended on by:** none yet (this is the terminal integration milestone for the current Selection Engine scope)

---

## 1. Objectives

Connect the completed, frozen Selection Engine (M1.0–M1.2) to the existing
Reader UI: when a lasso stroke completes, automatically resolve it via the
existing `SelectionEngine` and `TextLayoutCache`, display the result through
the existing overlay system, and route the resolved text into the existing
highlight/Ask AI/chat workflow — without redesigning, modifying, or
duplicating any logic already implemented in the four `selection.*`
packages, networking, authentication, or repositories.

## 2. Architectural Decisions

- **Pure orchestration, zero reimplementation.** `ReaderViewModel.onLassoStrokeCaptured`
  calls `textLayoutCache.getContentLayout(pdfId, pageIndex)` then
  `selectionEngine.resolve(polygon, layout)` and does nothing else with
  their internals — no matching, intersection, threshold, or reading-order
  logic exists in `ui.reader`. This directly satisfies requirement 7 ("do
  not duplicate any selection logic already implemented inside
  SelectionEngine").
- **`SelectionResult.selectedText` flows through the existing
  `onSelectionChanged` entry point**, not a new one — the same function the
  long-press text panel has always called. Everything downstream
  (`saveHighlight`, the `onAskAi` navigation callback, the Highlight/Chat
  screens) is completely unaware which tool produced the text it's
  consuming. This is what satisfies "preserve existing Highlight, Ask AI,
  Notes, and Chat flows by reusing the current interfaces" literally,
  rather than by parallel-but-equivalent code paths.
- **New UI is a thin presentation layer, not new business logic.** The one
  new composable, `LassoSelectionActionBar`, wires its Highlight/Ask AI
  buttons to the *exact same* `viewModel.saveHighlight(...)` call and
  `onAskAi` callback the existing `SelectableTextPanel` already uses,
  verbatim. It exists only because the lasso path had no UI trigger for
  those actions before; it does not introduce a second way to save a
  highlight or start a chat.
- **The existing overlay system is entirely unmodified.** `PolygonOverlay`
  and `LiveStrokeOverlay` (M1.0) still render `lassoPolygon` exactly as
  before; M1.3 only changes *what else* happens once resolution completes,
  never how the shape itself is drawn — satisfying requirement 3 by not
  touching it.
- **Failures fail locally, not globally.** A `try`/`catch` around the
  `TextLayoutCache`/`SelectionEngine` calls resets only lasso-scoped state
  (`lassoPolygon`, `lassoSelectionResult`, `currentSelection`) on exception,
  deliberately never setting `ReaderUiState.errorMessage` — the field that
  would surface a page-level error banner. A resolution failure is
  invisible to the rest of the reader, per requirement 9.
- **In-flight resolution is cancellable, mirroring the existing
  `highlightsJob` pattern.** A new `selectionResolutionJob: Job?` field is
  cancelled and replaced on every new stroke, tool switch, and page
  navigation — the same cancel-then-relaunch shape already used for
  `highlightsJob` in this exact file since M1.0, applied to a second
  scenario with the same underlying race (a slow, superseded async result
  arriving after a newer one and stomping current state).
- **Opportunistic cache warming for responsiveness.** `loadPage` now kicks
  off a best-effort, `runCatching`-wrapped prefetch of the current page's
  `PageContentLayout` via the same `TextLayoutCache` call `onLassoStrokeCaptured`
  uses. This directly serves requirement 8 ("must feel immediate and
  responsive") for the common case — draw a lasso any time after a page has
  been visible for even a moment — without adding any new caching
  mechanism; it's the same cache, called slightly earlier, with its result
  discarded (the point is purely to have `TextLayoutCache` already warm).

## 3. Files Created

None. This milestone is integration-only, entirely within existing files.

## 4. Files Modified

- `ui/reader/ReaderViewModel.kt`:
  - Constructor now takes `textLayoutCache: TextLayoutCache` and
    `selectionEngine: SelectionEngine` (both already Hilt-injectable from
    M1.1/M1.2 — zero new modules required).
  - `ReaderUiState` gained `lassoSelectionResult: SelectionResult?`.
  - `onLassoStrokeCaptured` extended to resolve through `TextLayoutCache`/
    `SelectionEngine` after the existing M1.0 geometry pipeline, with
    job-cancellation and graceful failure handling.
  - `setSelectionTool` fixed to also clear `lassoSelectionResult` and
    `currentSelection` (previously only cleared `lassoPolygon` — a gap that
    would have let a resolved lasso's text remain "active" in the text
    panel after switching tools).
  - `loadPage` fixed to clear all lasso-related state *immediately*, not
    only once the async bitmap/text load completes, and to cancel any
    in-flight resolution job; also now kicks off the cache-warming
    prefetch described above.
  - `clearLassoPolygon` extended to also cancel in-flight resolution and
    clear `lassoSelectionResult`/`currentSelection`, via a new shared
    private `clearLassoState()` helper also used by the failure path.
- `ui/reader/ReaderScreen.kt`:
  - New `LassoSelectionActionBar` composable, shown when
    `selectionTool == LASSO && currentSelection.isNotBlank()`, wired to the
    existing `saveHighlight`/`onAskAi`/`clearLassoPolygon`.
  - `ReaderScreen`'s public signature is unchanged — `NavGraph.kt` required
    no updates.
- `selection/textlayout/PACKAGE_STATUS.md`, `selection/engine/PACKAGE_STATUS.md`:
  documentation-only updates correcting a now-stale "not yet wired into the
  UI" note in each, found during the audit (see §5).

## 6. Known Limitations

- `SelectionEngine.resolve` is called with its default `SelectionEngineConfig`
  (0.35 overlap ratio) — M1.3 does not expose overlap-threshold tuning in
  the UI; this was never a requirement of this milestone (M1.2 already made
  it configurable at the engine level, which is sufficient).
- The brief window between a polygon being shown (`lassoPolygon` set) and
  its resolution completing (`currentSelection`/`lassoSelectionResult` set)
  does not clear a *previous* stroke's still-showing action bar — a
  deliberate choice (see §2) favoring responsiveness over eliminating a
  sub-second visual transition; documented rather than "fixed" to avoid
  trading a real UX cost (flashing the action bar away and back on every
  stroke) for a cosmetic one.
- The cache-warming prefetch in `loadPage` is best-effort only; if it fails
  or hasn't completed by the time a user draws a lasso, `onLassoStrokeCaptured`
  simply populates the cache itself on demand, exactly as it always could —
  there is no behavioral dependency on the prefetch succeeding.

## 7. Risks

- The state-management fixes in `setSelectionTool`/`loadPage`/`clearLassoPolygon`
  were verified by tracing every `.copy(...)` call site by hand, not by
  executing the app — the first on-device test should specifically exercise
  the "resolve a lasso, then immediately switch to TEXT mode" and "resolve
  a lasso, then immediately flip pages" sequences this milestone's fixes
  target.
- `onLassoStrokeCaptured`'s try/catch around `TextLayoutCache`/`SelectionEngine`
  is broad (`catch (e: Exception)`), matching the existing exception-handling
  style already used elsewhere in this file (e.g. `loadPage`'s own catch
  block) — consistent with established precedent, but means a genuine bug
  inside those components would also be silently swallowed here rather than
  surfaced. Acceptable given requirement 9's explicit "gracefully clear...
  without affecting the existing reader," but worth keeping in mind if
  selection failures ever need to be diagnosed from user reports.

## 8. Next Milestone

No further Selection Engine milestone is currently scoped. Natural
candidates for a future M1.4, none started: exposing `lassoSelectionResult.matchedBlocks`
for a richer selection-confirmation UI (e.g. highlighting only the matched

optionally persist a selection's bounding polygon so a lasso-created
highlight can be visually re-drawn on reopen, not just its text.
